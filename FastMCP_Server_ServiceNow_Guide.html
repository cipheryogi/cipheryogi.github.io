FastMCP Server for ServiceNow Instances

One Python script wraps the ServiceNow Table API as 60 MCP tools. Register the same command once per instance, change only the environment variables, and an AI client can read and write platform tables, Flow Designer logs, generative AI logs and the whole AI Agent Studio object model across every instance you work on, with nothing hosted and nothing listening on a network port.

60 tools over stdio One script, N instances Python 3.13 · uv · FastMCP Basic Auth or OAuth Nothing listens on a port Native console compared

Companion guides: Claude Code File Structure & Configuration (where instructions, settings, MCP configuration and credentials live) and Claude Code Capabilities (tools, agents, skills, hooks, permission modes, models and automation).

1. What This Setup Is

One Python script, launched once per ServiceNow instance, exposing 60 tools to an MCP client.

The problem it solves. You want an AI client, Claude Code or any other MCP-capable client, to read and write ServiceNow data across several instances without building a separate integration per instance and without hosting anything. The answer here is deliberately small.

One scriptserver_single.py is a FastMCP server that wraps the ServiceNow Table API as 60 tools. You add a tool by editing this one file.
One process per instanceThe same command is registered once per instance. Only the environment variables differ, so the script reads which instance to talk to at start-up. There is no per-instance branch in the code.
Two launchersClient A is Claude Code, running the script from a project folder. Client B is a second desktop MCP client with its own local copy. Both run server_single.py over stdio.
Many instances, one patternEach instance gets its own server entry with the same command, all over Basic Auth. Personal dev instances can use an admin account; customer instances should use a dedicated service account. Examples are in section 5.

Step 1 · Create the project folder

Create the folder and put two files in it: server_single.py, whose structure section 8 describes, and pyproject.toml.

mkdir -p "<project-root>/mcp-server"
cd "<project-root>/mcp-server"

The whole of pyproject.toml:

[project]
name = "mcp-server"
version = "0.1.0"
description = "ServiceNow MCP server"
readme = "README.md"
requires-python = ">=3.13"
dependencies = [
  "mcp[cli]>=1.27.0",
  "python-dotenv>=1.2.2",
  "requests>=2.33.1",
]
Check: ls shows pyproject.toml and server_single.py. Create an empty README.md as well, because pyproject.toml names it.

Step 2 · Create the shared virtual environment

Point uv at one environment outside the project folder, then install the dependencies into it. All servers share this environment.

export UV_PROJECT_ENVIRONMENT="$HOME/.venvs/mcp-server"
cd "<project-root>/mcp-server"
/opt/homebrew/bin/uv sync

Check the environment is real and the dependencies import:

~/.venvs/mcp-server/bin/python --version                            # prints Python 3.13.x
~/.venvs/mcp-server/bin/python -c "import mcp, requests, dotenv"     # prints nothing

Step 3 · Test the script by hand

Run it with the three environment variables set for one instance. This proves the script and its dependencies work before the AI client is involved.

cd "<project-root>/mcp-server"
SN_INSTANCE="https://<instance-a>.service-now.com" \
SN_USERNAME="<username>" \
SN_PASSWORD="<password>" \
UV_PROJECT_ENVIRONMENT="$HOME/.venvs/mcp-server" \
/opt/homebrew/bin/uv run python server_single.py
Check: the terminal prints [OK] Connected, then a short banner between two lines of = signs, and then waits. Press Ctrl+C to stop it.
Caveat. That output appears even if the credentials are wrong, because the script does not call the instance at start-up. Section 13 covers it.

Step 4 · Register one server per instance

Use the Claude Code CLI at user scope so the servers are available in every project. Repeat for each instance, changing the server name, URL, username and password. The variable names stay the same for every instance, only the values change.

claude mcp add servicenow-sn-<instance-a> --scope user \
  -e SN_INSTANCE="https://<instance-a>.service-now.com" \
  -e SN_USERNAME="<username>" \
  -e SN_PASSWORD="<password>" \
  -e UV_PROJECT_ENVIRONMENT="$HOME/.venvs/mcp-server" \
  -- /opt/homebrew/bin/uv --directory "<project-root>/mcp-server" run python server_single.py

claude mcp add servicenow-sn-<instance-b> --scope user \
  -e SN_INSTANCE="https://<instance-b>.service-now.com" \
  -e SN_USERNAME="<username>" \
  -e SN_PASSWORD="<password>" \
  -e UV_PROJECT_ENVIRONMENT="$HOME/.venvs/mcp-server" \
  -- /opt/homebrew/bin/uv --directory "<project-root>/mcp-server" run python server_single.py

The result is stored in the Claude Code user config. One entry looks like this:

"servicenow-sn-<instance-a>": {

Step 5 · Restart the client and confirm the tools

Restart the editor window or the CLI session. Tools are named mcp__<server name>__<tool name>, for example mcp__servicenow-sn-<instance-a>__sn_query.

Check: asking the client to list its ServiceNow tools shows 60 per server.

Step 6 · Prove it reaches the instance

Ask the client: "Using the <instance-a> server, query sys_user with limit 1." A returned record proves the whole chain: client, stdio, the script, HTTPS, Basic Auth, the instance.

Check: the reply contains a record with a sys_id. An HTTP 401 means the username or password is wrong.

Step 7 · Optional: avoid permission prompts for read tools

Add entries such as mcp__servicenow-sn-<instance-a>__sn_query to the permissions.allow list in ~/.claude/settings.json. Leave write and delete tools off the list so the client still asks first.

6. Setup B: A Second Desktop MCP Client

The second runtime. A separate copy of the script, launched by a second desktop client application.

Client B is any second desktop MCP client that can launch a stdio server. The transferable part is the shape: its own copy of the script, its own virtual environment, and an integrations.json that stores the environment values as placeholders.

Step 1 · Create the Client B project folder

Client B runs its own copy. Create ~/<client-b-folder> and place server_single.py (Script B), pyproject.toml with the same dependencies, and .python-version containing 3.13 in it.

mkdir -p "$HOME/<client-b-folder>"
cd "$HOME/<client-b-folder>"
/opt/homebrew/bin/uv sync
Check: a .venv folder now exists inside the Client B folder. Unlike Script A, this copy uses its own environment, not the shared one.

Step 2 · Get Script B

Script B is Script A with the start-up code changed: no OAuth support, and it loads a .env from its own folder rather than using python-dotenv's default search. The easiest way to produce it is to copy Script A and apply the differences listed in section 13. Both copies expose the same 60 tool names.

Step 3 · Add one MCP server per instance in Client B

In the client application, add a stdio MCP server with this command, once per instance, with the three variables SN_INSTANCE, SN_USERNAME and SN_PASSWORD.

/opt/homebrew/bin/uv --directory ~/<client-b-folder> run server_single.py

Client B records each server in ~/Library/Application Support/<client-b>/integrations.json under mcp_servers. The env values are stored as placeholders of the form $MCP_ENV_<server-id>_SN_USERNAME, and the client substitutes the real value when it launches the process.

Two things to expect here. Menu labels vary by client version, so look for whatever the application calls adding a local or stdio MCP server. And where the client keeps the resolved value behind each $MCP_ENV_* placeholder is not documented, so treat the credential as present on the machine in some form and rotate it accordingly.

Step 4 · Confirm Client B started it

ps aux | grep <client-b-folder>
Check: a process running ~/<client-b-folder>/.venv/bin/python3 server_single.py whose parent is uv --directory ~/<client-b-folder> run server_single.py, started by the client application's bundled helper binary.

What this means in practice

  • Both launchers pass the three variables in the process environment, so the project-folder .env is never consulted for them. python-dotenv does not override variables that are already set.
  • The only .env in the project folder holds one instance and goes stale. It can be deleted without changing behaviour. Do not use it as the place to add new instances.
  • The instance value may be a full URL such as https://<instance>.service-now.com, a bare name such as <instance>, which becomes the full URL, or a host name. The script normalises all three.
  • Passwords are never written into the script. A search of Script A for hardcoded credentials and instance URLs found none.

8. How a Tool Call Works

Every tool is a Python function that calls ServiceNow's REST API and returns JSON text.

sequenceDiagram
  autonumber
  actor U as You
  participant C as AI client
  participant S as server_single.py · FastMCP over stdio
  participant K as ServiceNowClient
  participant N as ServiceNow instance
  U->>C: Show me the last 5 failed flow logs
  C->>S: tools/call sn_query_flow_logs · JSON over stdin
  S->>K: table_get on sys_flow_log with query and limit
  K->>N: GET /api/now/table/sys_flow_log · Basic Auth · 30 s timeout
  N-->>K: 200 with a result array
  K-->>S: success true, plus the data payload
  S-->>C: JSON text string of records
  C-->>U: Summary written from the records

The pieces inside server_single.py

PieceApproximate locationWhat it does
ServiceNowClientlines 16 to ~180Builds the base URL, holds one requests.Session, applies Basic Auth, or OAuth when a client id and secret are set, sets JSON headers and a 30 second timeout. Every response comes back as {success, status_code, data, error}.

qh() helper~line 268Quick query helper used by most read tools. Caps the limit at 1000 and defaults to display values.

Guard rails in the code. Every delete tool, and batch delete, refuses to run unless confirm=True is passed. Most other writes have no guard, so the client's permission prompt is the safety net.

Three kinds of tool

1

Generic Table API wrappers

Query, get, create, update, delete and aggregate against any table you name.

Think: the raw platform, with a permission prompt in front of it.

2

Domain wrappers

The table and field names are fixed in the function, so the model does not have to know the AI agent object model to ask a useful question.

Think: a named question, not a table scan.

3

Tools with real logic

Multi-record operations such as sn_create_ai_agent, sn_create_rag_pipeline, sn_clone_ai_agent and sn_add_record_operation_tool.

Think: a small piece of automation behind one call.

2. One representative tool definition and the helper almost every read tool calls:

@mcp.tool()
def sn_query(table: str, query: str = "", fields: str = "", limit: int = 20) -> str:
    """Query any table on the active instance."""
    return qh(table, query, fields, limit)


def qh(tbl: str, qry: str = "", flds: str = "", lmt: int = 20,
       ob: str = "-sys_created_on", dv: bool = True) -> str:
    """Quick helper for table queries."""
    fl = [f.strip() for f in flds.split(",")] if flds else None
    r = client.table_get(tbl, query=qry or None, fields=fl,
                         limit=min(lmt, 1000), order_by=ob,
                         display_value="true" if dv else "false")
    if r["success"]:
        return json.dumps({"count": len(r["data"].get("result", [])),
                           "records": r["data"].get("result", [])}, indent=2)
    return json.dumps({"error": r["error"]}, indent=2)

3. The Table API request helper:

def table_get(self, table: str, sys_id: str = None, query: str = None,
              fields: list = None, limit: int = 100, offset: int = 0,
              order_by: str = None, display_value: str = "false") -> dict:
    endpoint = (f"/api/now/table/{table}/{sys_id}" if sys_id
                else f"/api/now/table/{table}")
    params = {
        "sysparm_limit": limit,
        "sysparm_offset": offset,
        "sysparm_display_value": display_value,
        "sysparm_exclude_reference_link": "true",
    }
    if query:    params["sysparm_query"] = query
    if fields:   params["sysparm_fields"] = ",".join(fields)
    if order_by: params["sysparm_orderby"] = order_by
    return self._request("GET", endpoint, params=params)

4. The single _request method every verb funnels through, which is what produces the uniform response envelope:

def _request(self, method, endpoint, params=None, data=None) -> dict:
    url = f"{self.base_url}{endpoint}"
    try:
        response = self.session.request(method=method, url=url, params=params,
                                        json=data, timeout=self.timeout)
        return {
            "success": response.ok,
            "status_code": response.status_code,
            "data": response.json() if response.text else None,
            "error": None if response.ok
                     else f"HTTP {response.status_code}: {response.reason}",
        }
    except Exception as e:
        return {"success": False, "status_code": None, "data": None, "error": str(e)}
The real method does a little more. On the OAuth path it fetches a bearer token before the call, and on a 401 with a refresh token present it refreshes once and retries.

12. Security Hardening

The setup works as described. These are the risks it carries, and how to reduce them.

Current state. The password for each Claude Code server sits in plaintext in the Claude Code user config. Client B keeps only placeholders in integrations.json, and where it stores the resolved values is not documented. Servers that run as an admin user give every tool call, including the delete and batch tools, full admin rights on the instance. Servers on service accounts can do only what those accounts' roles allow.

Recommended changes

1. A dedicated service user per instance

Give it only the roles the tools need, instead of admin. A read-only user is enough if you only use the query and inspection tools.

2. Prefer OAuth where possible

Script A supports the OAuth password grant when SN_CLIENT_ID and SN_CLIENT_SECRET are set. It lets you revoke access without changing the user's password. Script B does not support it.

3. Keep secrets out of synced folders

Do not put a .env holding credentials in a cloud-synced project folder. It is copied to the cloud and to your other devices.

4. Keep write tools behind prompts

Only allow-list the read tools in settings.json. Leave create, update and delete tools to prompt every time.

5. Rotate in every place

When a password changes, update each location that stores it: the matching entry in the Claude Code user config, the matching server's env values in Client B, and any other tool holding the same credential.

6. Do not share the config files

They are personal. Share this guide, which contains no credentials, instead.

Platform baseline assumed here

  • Both instances in this example run a recent Australia patch with the Model Context Protocol Server plugin (sn_mcp_server) and the client plugin (sn_mcp_client) installed.
  • Each instance already had several provisioned MCP servers in sn_mcp_server_registry, for example sn_itsm_mcp_server.itsm_default, sn_hr_mcp_server.hr_default and sn_csm_mcp_server.csm_default.

Which one to reach for

Building and debugging agents

Use the FastMCP setup. You need broad table access across several instances, and you are the only user.

Reading and updating business records

Use the native console, so calls run under a real user's permissions rather than as admin.

Anything you hand to someone else

Use the native console. The server, its tools and the consent are records on the instance, which is what makes the access reviewable.

Step 2 · Create the Scripted REST API and the GET resource

Go to All > System Web Services > Scripted REST APIs. Create an API named Incident API with API ID incident_api and Default ACLs Scripted REST External Default. Add a resource Get Incident: method GET, relative path /{number}, the same default ACLs, with this script.

(function process(/*RESTAPIRequest*/ request, /*RESTAPIResponse*/ response) {
  var number = request.pathParams.number;
  if (!number) {
    response.setStatus(400);
    response.setBody({ message: "Incident number is required." });
    return;
  }
  var gr = new GlideRecord('incident');
  gr.addQuery('number', number);
  gr.query();
  if (gr.next()) {
    response.setStatus(200);
    response.setBody({
      sys_id: gr.getValue('sys_id'),

})(request, response);

Step 3 · Add the POST resource and its OpenAPI schema

On the same API add a resource Update Incident: method POST, relative path /{number}, the same default ACLs, with this script.

(function process(/*RESTAPIRequest*/ request, /*RESTAPIResponse*/ response) {
  var number = request.pathParams.number;
  if (!number) {
    response.setStatus(400);
    response.setBody({ message: "Incident number is required." });
    return;
  }
  try {
    var params = request.body.data;
    var gr = new GlideRecord('incident');
    gr.addQuery('number', number);
    gr.query();
    if (!gr.next()) {
      response.setStatus(404);
      response.setBody({ message: "Incident not found: " + number });
      return;
    }
    for (var key in params) {
      if (params.hasOwnProperty(key)) {
        if (key === 'work_notes' || key === 'comments') {
          gr[key] = params[key];
        } else {
          gr.setValue(key, params[key]);
        }
      }
    }
    gr.update();
    response.setStatus(200);
    response.setBody({
      message: "Incident updated successfully.",
      number: gr.getValue('number'),
      sys_id: gr.getUniqueValue()
    });
  } catch (e) {
    response.setStatus(500);
    response.setBody({ message: "Error occurred: " + e.message });
  }
})(request, response);

16. Quick Decision Guide

Five questions that place you in the right section of this guide.

FastMCP setup

“I am building and debugging AI agents, and I need broad table access across several instances.”

Use this setup. Register the same command once per instance with its own SN_INSTANCE, SN_USERNAME and SN_PASSWORD, as in section 5, and read the server part of each tool name to know which instance answered.

Native console

“Someone else will use this against real business records.”

Use the native MCP Server Console instead, as sections 14 and 15 describe. Calls then run under the consenting user's permissions and ACLs, and the server, its tools and the consent are all records on the instance.

Troubleshooting

“My server shows as failed, or every tool call returns an error.”

Run the script by hand with the three variables, step 3 of section 5, and read the error. A start-up banner is not proof of a working credential, so confirm with the curl check in row 4 of section 10 before you change anything else.

Two copies

“I added a tool, but one of my clients still cannot see it.”

The two clients run two separate copies of the script. Edit the copy that client launches, then restart the client so it relaunches the process. Sections 6 and 13 cover the drift and what to do about it.

Credentials

“Where do the passwords live, and what has to change when one is rotated?”

In the client configuration, in plaintext, and the process environment always wins over any .env file. Section 7 traces the resolution order, and section 12 lists every place a rotated credential has to be updated.
